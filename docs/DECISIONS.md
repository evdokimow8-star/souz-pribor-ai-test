# Промпт, проверяемость и границы решения

## Почему такой объём

Задание ограничено локальным прототипом на 2–4 часа. Интерфейс и сервер работают на стандартной библиотеке Python; установку зависимостей и сборку frontend делать не нужно. Код разделён на входной контракт, работу с моделью, HTTP и интерфейс.

Стандартный `http.server` здесь — осознанный выбор для локальной демонстрации. Это не публичный production-сервер. При развитии в многопользовательский сервис HTTP-слой следует заменить ASGI-приложением, добавить авторизацию и квоты.

## Интерфейс и сохранение работы

Редактор сразу показывает сохранённый ответ настоящего API. На телефоне работа разделена на карточку, данные и проверки; на широком экране форма и результат расположены рядом. Экспорт доступен рядом с результатом, а форма поддерживает обычные поля и строгий JSON без потери повторяющихся ключей.

Для каждого примера сохраняются исходный ввод, последний успешный ответ и отдельная ручная редакция. Изменение входа не уничтожает ответ: интерфейс явно помечает его как предыдущую версию. Сохранение и восстановление имеют общий предел размера состояния; при невозможности сохранения появляется предупреждение, без обрезания текста. Лимит HTTP-запроса проверяется отдельно по UTF-8-байтам.

Ручное редактирование не делает нового запроса. После него формальная проверка исходного ответа не приписывается новому тексту: интерфейс и JSON требуют проверки редактором, доказательства остаются привязаны к первоначальному ответу модели. Характеристики из входа не меняются.

Черновики сохраняются транзакцией IndexedDB. Она читает последнюю версию и проверяет конфликт перед записью. Старые данные из `localStorage` импортируются в пустую базу. Восстановленная структура проверяется, текст вставляется через `textContent`, ссылки разрешены только HTTP(S). Закрытые данные не стоит оставлять в общем браузерном профиле.

## Промпт

Полный действующий промпт находится в `pribor/llm.py`, `SYSTEM_PROMPT`. В системном сообщении задаются роль технического редактора, формат, длина и запрет на добавление свойств. Пользовательское сообщение содержит сериализованный реестр исходных фактов с идентификаторами, список недостающих полей и замечания.

Содержимое товара не интерполируется в системную инструкцию. Промпт явно объявляет его недоверенными данными, запрещает исполнять вложенные команды, обращаться по ссылкам и достраивать свойства по памяти о названии модели.

Используется `response_format: json_schema`, для OpenRouter — `require_parameters: true`. Поддержка параметра зависит от endpoint. Даже structured outputs не заменяют локальную проверку.

Описание направляется в три абзаца ограниченной длины, чтобы проще выполнить общий лимит. При этом локальный контракт принимает 2–5 абзацев при соблюдении общего объёма задания. Сложные формулы погрешности оставляются точной таблице: их сокращённый пересказ может менять границы применимости.

## Что программа проверяет сама

1. Типы, размеры и дубли ключей входного JSON.
2. Набор полей ответа и обязательные ссылки каждого блока на известные факты.
3. Длины заголовка и описания, количество и различие поисковых запросов.
4. Новые числа, включая знак, пары «число + единица» и порядок границ диапазона в сравнении с указанными фактами.
5. Неизвестные технические обозначения и единицы, включая IP, интерфейсы и единицы после числа.
6. Часть неподтверждённых обещаний и деталей конструкции/комплектации.
7. Частичный пересказ сложной погрешности.

Характеристики модель вообще не редактирует: таблица строится из исходного `specs`. Неизвестные значения сохраняются как «данных нет». Противоречия, замеченные при подготовке примеров, занесены во входные `notes`, а не выдаются за автоматически обнаруженные моделью.

Если проверка не пройдена, сервер возвращает структурированную ошибку с причинами. Скрытой подмены ответа шаблоном и автоматических платных повторов нет. Повторный запрос — отдельное действие пользователя.

## Что эта защита не доказывает

Разрешённое число можно приписать неправильному параметру; правильную ссылку на факт можно использовать для ложного утверждения; новое качественное свойство может не содержать цифр. Prompt injection также нельзя считать полностью решённой одной системной инструкцией.

Поэтому интерфейс показывает происхождение блоков и требует редакторской проверки. Нельзя обещать «нулевые галлюцинации». Следующий полезный шаг — размеченный набор примеров с технической экспертизой, отдельная проверка смысловых утверждений и оценка доли принятых черновиков для каждой модели.

## Ошибки и безопасность

- Неверный ключ, недостаток средств, rate limit, сеть, тайм-аут, обрезанный и повреждённый ответ обрабатываются отдельно.
- Неоднозначный тайм-аут не повторяется автоматически: предыдущий запрос мог быть оплачен.
- Ключ не отправляется в UI; сырые ошибки провайдера не показываются пользователю.
- Redirect API запрещён, чтобы не переносить Authorization на другой хост.
- Внешние API требуют HTTPS. Входной `source_url` служит ссылкой для человека, не выполняется сервером.
- Сервер доступен только через loopback; посторонние Origin и Host блокируются.
- Вывод в браузере создаётся через `textContent`, HTML от модели не исполняется.
- Есть CSP, ограничение тела запроса и один одновременный вызов модели.

## Стоимость и воспроизводимость

Сохранённые примеры — реальные ответы API, не ручные шаблоны. Данные модели и стоимость отдельного ответа находятся рядом с его JSON; цена берётся из `usage.cost`, не рассчитывается по длине текста. Просмотр примера бесплатен.

LLM недетерминированна: при том же входе новый ответ может отличаться. Поведение тестов воспроизводится с подменённым сетевым транспортом. Промпт и версия схемы хранятся в Git; вход сохранённого примера связан SHA-256.

## Возможное развитие

Приоритеты: корпус проверенных карточек; профиль обязательных полей для каждого типа прибора; проверка противоречий и формул; поддержка паспортов с цитатами; сравнение редакций; явное одобрение редактором; бюджеты и журнал операций. Подключать CMS и массовые очереди имеет смысл после оценки качества черновиков.
